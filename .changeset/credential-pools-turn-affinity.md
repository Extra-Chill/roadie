Credential pools: turn affinity and a Discord-first empty-pool message (issue #137, items 1-2). Turn affinity: the pool provider now reads `x-roadie-session` from the call headers before stripping them and holds a live route per session — pool, account, provider/model, pinned under the rotation name — in a new `<dataDir>/credentials/routes.json` (mode 0600) behind its own in-process lock (`cli/src/credentials/routes.ts`, separate from the pool locks), with a 30-minute TTL as the safety net for a missed idle event and expired entries pruned on every write. The first successful dispatch of a turn pins the route; later requests of the same session try the held candidate first, so tool follow-ups never split across accounts (and, once mixed-provider rotations exist, never across providers mid-turn). The route only moves when the held account itself fails — a 429 cooldown or a failed OAuth refresh — and success re-pins to the candidate that answered. The credential-pools plugin gains an `event` hook that clears the session's route on `session.idle` and `session.deleted` (the same lifecycle subrouter uses); requests without a session header, routes whose rotation no longer matches (a `/model` switch), routes whose pool fell out of the request's pool list, and held accounts that are cooling down or removed all behave exactly as before, and the resolved candidate set is never expanded, so fail-closed 401s, per-person/fallback lists and any-provider routing are unchanged. Empty-pool 401s now lead with the Discord commands a server member can actually run — `add one with /credentials add-key or /credentials login-anthropic` — and keep the `roadie credentials ...` CLI hint for operators in parentheses.
